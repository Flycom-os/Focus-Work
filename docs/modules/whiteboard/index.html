🎨 Модуль Whiteboard (Аналог Miro / tldraw)

Этот модуль представляет собой бесконечный интерактивный холст для совместного проектирования, рисования интерфейсов и проведения онлайн-митингов в реальном времени.

🌟 1. Введение и концепт

В отличие от классического веба, где интерфейс статичен и состоит из форм, полей и кнопок, виртуальная доска — это двумерное графическое пространство.

Здесь действуют законы компьютерной графики:

  • Бесконечный холст (Infinite Canvas): Плоскость не ограничена размерами экрана. Пользователь может скроллить (pan) и масштабировать (zoom) холст во всех направлениях.
  • Векторные элементы: Фигуры (квадраты, круги), стикеры с текстом, соединительные линии со стрелочками и свободное рисование пером. Все элементы хранятся как математические координаты, а не как картинки.
  • Real-time Коллаборация: Пользователи видят курсоры друг друга с именами в реальном времени, а также мгновенно наблюдают процесс создания или перемещения фигур.
💡 Аналогия для джунов: Представьте, что доска — это лист бумаги, лежащий на огромном столе. А ваш монитор — это рамка от картины, которую вы держите в руках над этим листом. Когда вы перемещаете руку — вы скроллите холст (pan). Когда вы приближаете или удаляете лицо от стола — вы меняете масштаб (zoom).

📊 2. Архитектура реального времени и Throttling

Пересылать координаты курсора мыши 60 раз в секунду в базу данных — верная смерть для любого сервера. Поэтому в архитектуре Whiteboard мы строго разделяем быстрые временные события (курсоры) и постоянные изменения (создание и редактирование фигур).

sequenceDiagram autonumber actor ClientA as Разработчик А actor ClientB as Разработчик Б participant WS as WebSocket Server (NodeJS) participant Redis as Redis Cache (Временный кэш) participant DB as PostgreSQL (Prisma DB) ClientA->>WS: mouse_move: { x: 120, y: 350 } WS-->>ClientB: broadcast: mouse_move (без записи в БД) ClientA->>WS: shape_update: { id: "shape-1", x: 200, y: 150 } WS-->>ClientB: broadcast: shape_update (синхронно обновляем экран у Б) WS->>Redis: Сохраняем промежуточное состояние фигуры Note over WS,Redis: Каждые 2 секунды (Throttling) WS->>Redis: Достаем батч накопившихся изменений WS->>DB: Запись в БД: prisma.shape.updateMany(...) DB-->>WS: Запись успешна. Временный кэш очищен.

Такой подход снижает нагрузку на PostgreSQL в 100+ раз! Даже если 50 человек будут одновременно перетаскивать стикеры, база данных выполнит всего 1 транзакцию записи раз в две секунды вместо тысяч одиночных обновлений.

🗄 3. Prisma-модели и Структура Фигур

Каждая доска содержит коллекцию фигур. Так как фигуры бывают разного типа (стикер, линия, полигон рисования пером), мы используем поле типа JSON для хранения специфичных свойств фигуры, сохраняя базовые координаты в индексируемых колонках для быстрого поиска по видимой области (Bounding Box). 

model Whiteboard {
  id          String         @id @default(uuid())
  name        String
  projectId   String         @unique // Доска привязана к проекту
  project     Project        @relation(fields: [projectId], references: [id], onDelete: Cascade)
  shapes      Shape[]
  createdAt   DateTime       @default(now())
  updatedAt   DateTime       @updatedAt
}

model Shape {
  id           String      @id @default(uuid())
  whiteboardId String
  whiteboard   Whiteboard  @relation(fields: [whiteboardId], references: [id], onDelete: Cascade)
  type         ShapeType   // RECTANGLE, CIRCLE, STICKER, ARROW, PATH
  x            Float       // Координата X на бесконечном холсте
  y            Float       // Координата Y на бесконечном холсте
  width        Float
  height       Float
  fill         String      @default("#ffffff") // Цвет заливки в HEX/RGBA
  stroke       String      @default("#000000") // Цвет обводки
  strokeWidth  Float       @default(2.0)
  text         String?     // Текст внутри стикера или фигуры
  properties   Json        // Дополнительные свойства (массив точек для пера, стрелочки и др.)
  lastUserId   String?     // Кто последний редактировал фигуру
  createdAt    DateTime    @default(now())
  updatedAt    DateTime    @updatedAt

  @@index([whiteboardId])  // Быстрая выборка фигур для конкретной доски
}

enum ShapeType {
  RECTANGLE
  CIRCLE
  STICKER
  ARROW
  PATH
}

⚖️ Архитектурный компромисс: Отдельные строки vs Один JSON-монолит

При проектировании бэкенда Whiteboard часто возникает дилемма: хранить каждую фигуру как отдельную запись в БД (как сделано у нас) или сохранять всю доску целиком как одну большую текстовую JSON-строку.

Подход Плюсы Минусы
Одна строка JSON на доску Супер быстрый рендеринг при загрузке. Простой бэкенд (один SQL-запрос). Невозможность совместной работы: если два пользователя одновременно изменят разные части доски, один перезапишет изменения другого («Race Condition»). Раздувание трафика.
Каждая фигура — запись в БД (Выбрано нами) Надежный реалтайм. Возможность блокировать отдельную фигуру (редактирует А, остальные видят замочек). Легко писать историю изменений (Undo/Redo). При загрузке доски с 10 000 фигур база возвращает 10 000 строк. Нужна оптимизация выборки и кэширование на стороне WebSocket-сервера.
