📁 Модуль Задач (Аналог YouTrack)

Этот модуль отвечает за весь таск-менеджмент внутри компании: от простейших личных заметок до сложных Scrum-спринтов, учета рабочего времени и автоматического построения диаграмм сгорания задач (Burndown Charts).

🌟 1. Введение и бизнес-логика

Чтобы понять, как устроен этот модуль, давайте представим обычную доску со стикерами в офисе. Каждый стикер — это Задача (Task). Она висит в определенной колонке — Статус (Column). Вы можете перетащить задачу руками в соседнюю колонку.

В Focus-Work мы реализовали этот функционал на стероидах:

  • Многоуровневость: Проекты ➡️ Доски ➡️ Спринты ➡️ Колонки ➡️ Задачи ➡️ Подзадачи.
  • Оценка времени (Estimation): Оценка задачи в часах (Story Points) с логами списания времени (Time Tracking).
  • Совместная работа: Несколько пользователей могут одновременно смотреть на одну доску. Если один из них перетянет задачу, у остальных она передвинется на экране автоматически за доли секунды (WebSockets).
💡 Аналогия для джунов: Представьте, что Kanban-доска — это витрина магазина. Задачи — товары, а колонки — отделы. Когда товар покупают, он не исчезает мгновенно из памяти, он переходит на склад. Так же и в БД: при переносе задачи в колонку "Выполнено", мы не удаляем ее, а просто меняем ее связь с колонкой.

📊 2. Архитектура и Data Flow

В основе модуля лежит концепция Optimistic Updates (Оптимистичные обновления). Это значит, что когда пользователь перетаскивает задачу, интерфейс реагирует мгновенно, не дожидаясь ответа от сервера. Если сервер вернул ошибку, карточка плавно возвращается на исходное место.

Схема жизненного цикла перемещения карточки (Drag & Drop Data Flow):

sequenceDiagram autonumber actor User as Разработчик (Браузер) participant UI as KanbanBoard Component participant Cache as React Query (State) participant Server as Next.js Server Action participant DB as PostgreSQL participant WS as WebSocket Server User->>UI: Перетаскивает задачу из Column A в Column B UI->>Cache: Срабатывает onDragEnd, обновляем кэш локально (Optimistic Update) UI->>Server: Вызов Server Action: updateTaskColumn(taskId, targetColumnId, newPosition) Server->>DB: Prisma update: меняем columnId и position у Task DB-->>Server: Успешно записано Server->>WS: Эмитим событие "task:moved" { taskId, colId, pos } WS-->>User: (Связующий сокет отправляет бродкаст другим клиентам) Server-->>UI: Возвращаем статус 200 OK Note over UI,Cache: Кэш подтвержден. Карточка остается на месте.

Если шаг 4 падает (например, пропал интернет или задача заблокирована другим процессом), React Query ловит ошибку, считывает сохраненный снимок состояния доски и откатывает кэш, возвращая карточку назад в Column A с анимацией.

🗄 3. Prisma-модели и Схема Базы Данных

База данных спроектирована на СУБД PostgreSQL. Схема описана с использованием ORM Prisma. Ниже представлены основные сущности, их поля и связи. 

model Project {
  id          String   @id @default(uuid())
  name        String
  key         String   @unique // Например: "PROJ", "CRM"
  description String?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  boards      Board[]
  tasks       Task[]
}

model Board {
  id        String   @id @default(uuid())
  name      String
  projectId String
  project   Project  @relation(fields: [projectId], references: [id], onDelete: Cascade)
  columns   Column[]
  createdAt DateTime @default(now())
}

model Column {
  id        String   @id @default(uuid())
  name      String
  position  Float    // Используется для сортировки колонок
  boardId   String
  board     Board    @relation(fields: [boardId], references: [id], onDelete: Cascade)
  tasks     Task[]
  createdAt DateTime @default(now())
}

model Task {
  id          String    @id @default(uuid())
  title       String
  description String?
  position    Float     // Сортировка внутри колонки
  statusId    String
  column      Column    @relation(fields: [statusId], references: [id], onDelete: Cascade)
  projectId   String
  project     Project   @relation(fields: [projectId], references: [id])
  assigneeId  String?
  assignee    User?     @relation("TaskAssignee", fields: [assigneeId], references: [id])
  creatorId   String
  creator     User      @relation("TaskCreator", fields: [creatorId], references: [id])
  priority    Priority  @default(MEDIUM)
  estimation  Int?      // Время в минутах
  timeSpent   Int       @default(0) // Залогированное время
  dueDate     DateTime?
  comments    Comment[]
  subtasks    Task[]    @relation("TaskToSubtask")
  parentId    String?
  parent      Task?     @relation("TaskToSubtask", fields: [parentId], references: [id], onDelete: Cascade)
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt
}

enum Priority {
  LOW
  MEDIUM
  HIGH
  CRITICAL
}

💡 Глубокий разбор: Почему позиции колонок и задач типа Float, а не Int?

Представьте, что у вас есть 10 задач в колонке, пронумерованных от 1 до 10. Пользователь перетаскивает задачу с позиции 10 на позицию 2.

Если бы мы использовали целые числа (Int), нам пришлось бы изменить индексы у ВСЕХ задач со 2 по 9 (сделать им +1). Это породило бы тяжелый запрос к базе данных, перезаписав 9 строк ради одного перемещения. А если в колонке 10 000 задач? База просто «ляжет» при активном перетаскивании.

Как решает это Float:

Мы назначаем задачам позиции с большим шагом, например: задача 1 имеет позицию 1000.0, задача 2 — 2000.0. Если мы перетаскиваем задачу 10 между задачами 1 и 2, новая позиция вычисляется как среднее арифметическое:
(1000.0 + 2000.0) / 2 = 1500.0

В итоге мы обновляем всего одну строку в базе данных! База данных чувствует себя прекрасно, а карточка встает ровно туда, куда нужно. Если позиции сблизятся слишком сильно (например, разница станет меньше 0.00001), срабатывает периодический фоновый скрипт пересчета индексов (rebalancing), который снова разносит их с шагом 1000.
